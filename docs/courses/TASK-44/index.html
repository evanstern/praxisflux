TASK-44 — The Reorient Plugin
Module 1

The Session That Became a Machine

One morning, a game project called promptworld had a pile of fresh research and a hard question: we researched how great games teach and how great games are documented — so what should we actually build? The owner didn’t want a summary. They wanted the project’s whole direction re-examined against one sentence: “this is a game that teaches AI-prompting skills, and it must be fun.”

What followed was a live, one-off working session: two AI evaluators read one research branch each, judged the project against that sentence, asked the owner eight sharp questions, folded the answers back in, cross-checked each other, and merged into a single plan that rewrote the project’s task board. It worked so well that the owner asked for it to be bottled — turned into a repeatable tool. TASK-44 is that bottling: the reorient plugin.

🧪
Good to know: dogfooding in reverse

Most tools are built first and tried later. reorient went the other way: the process ran once, live, on a real project — decisions, dead ends, and all — and only the parts that proved themselves were written down as the plugin. The best spec turned out to be a transcript.

Everything starts with a lens

The single most important input isn’t the research — it’s the lens. Research is neutral by design; a lens gives it a direction to push against. In the promptworld session, the lens even contradicted the research’s own framing: the notes had been gathered assuming “an ambient simulation you watch,” but the lens said “a learning game you write prompts at.” Spotting that clash — and ruling that the lens wins — became the deepest finding of the whole run.

That’s why the plugin refuses to open a run without one. A reorientation without a purpose statement is just a book report. Here is what opening a run actually looks like — the exact command, translated:

COMMAND — opening a reorient run 

node scripts/run.mjs begin . \
  --lens "a game that teaches prompting skills, and it must be fun" \
  --corpus research/Game-Gameplay-Patterns \
  --corpus research/Game-Player-Docs
PLAIN ENGLISH

Open a tracked reorientation run on this project (the dot means “right here”).

This is the lens — the one sentence every evaluation will push against. Refusing to start without it is the point.

Evaluate this research branch (how games create engaging play)…

…and this one (how games teach and document themselves) — one evaluator each, in parallel.

What one run produced

The live session that became this plugin ran the loop once, on two research branches, and left behind: eight operator decisions recorded mid-flight, two cross-grounded analysis notes (one per branch), one synthesis document with an explicit “do we need a massive refactor?” assessment (verdict: no — with reasons), and thirteen task-board moves: priorities raised, tasks rescoped, seven new tasks created, one research follow-up commissioned. Every artifact still exists and is still load-bearing in that project today.

💡
Key insight: the residue IS the product

The conversation that produced all this is gone — conversations always are. What makes the loop worth a plugin is that every phase leaves a durable artifact: a run record, analysis notes, a synthesis, board entries. Anyone (or any AI) arriving next week can reconstruct not just what was decided, but why.

Module 2

A Manifest, Not a Promise

The owner made one design call that shaped the whole plugin: require nothing. A project might have a research vault, a wiki, and a task board — or none of them. reorient must run anywhere, on any pile of notes.

That flexibility creates a trap. A tool that requires a wiki can promise “every claim was checked against the wiki.” A tool where everything is optional can promise… what, exactly? The answer reorient landed on: promise exactly what you detected, in writing, and let the checker hold you to precisely that.

The run record is the contract

When a run opens, the plugin writes a small manifest recording the lens, every research branch being evaluated, and — crucially — which optional surfaces it actually found. Here is the detection, verbatim from the plugin:

CODE — reorient/scripts/run.mjs 

export function detectGrounding(root, corpus) {
  return {
    vault: corpus.some((c) => c.kind === "vault-branch"),
    wiki: existsSync(join(root, "docs", "wiki")) ? "docs/wiki" : null,
    board: existsSync(join(root, "backlog")),
  };
}
PLAIN ENGLISH

A little routine: given the project folder and the list of research branches…

…answer three yes/no questions and hand the answers back:

Is any of the research proper vault research (versus a loose folder of notes)?

Does a wiki folder exist? Remember where; write down “none” otherwise.

Does a task board exist?

That’s the whole answer…

…and the whole routine. No configuration, no guessing — just looking.

Nothing here fails when something is missing. Absence isn’t an error — it’s a fact that gets recorded, and the skill tells the user plainly how the run degrades: no wiki means evaluators ground against the README instead and say so; no board means “board moves” become a proposed-task list.

The checker demands exactly what you recorded

Every praxisflux plugin ends in a gate, and reorient’s gate reads the manifest first. One line shows the trick — this is from the list of sections the final synthesis document must contain:

CODE — reorient/gates/reorient.mjs 

{ name: "Board moves", re: /(^|\n)#+\s+.*board/i, when: (run) => !!run.grounding?.board },
PLAIN ENGLISH

“The synthesis must have a Board moves section — but only WHEN this run’s manifest recorded that a board actually exists.”

The same scaling runs through the whole gate: only branches recorded as vault branches must carry a formal analysis note; the “Board moves” section is only demanded of projects that have a board. And two demands never relax: the synthesis must live outside every research branch (it’s the connective tissue the vault’s isolation rule forbids the branches from holding), and it must mention every branch by name — a “merge” that never names a branch didn’t merge it.

⚖️
Good to know: the gate never writes

By suite convention the checker is read-only — it can refuse, but it can never “fix.” Exactly one script (the run tracker) is allowed to write run records. Splitting the writer from the judge is what makes the judge trustworthy.

No walking away mid-run

One more piece rides along: a Stop hook. While a reorientation run is in flight, the AI assistant cannot simply end its session and wander off — the hook checks the run record, finds the missing artifacts, and blocks with instructions: finish it (land the analyses and the synthesis, then run finish) or close it honestly with abandon <reason>. Either way the run record survives as residue. An abandoned reorientation is a recorded fact; a silently evaporated one is a lie by omission.

Module 3

Steering a Team You Can’t Interrupt

Here is the awkward physics of parallel AI teamwork: the evaluator subagents cannot talk to the human. They can’t pause to ask “wait — do you want scores, or just a story?” But a reorientation is full of questions only the owner can answer. The promptworld session hit eight of them.

reorient’s answer is checkpointed relay: evaluators end every draft with a section literally titled “open questions for the operator”; the lead digests each draft for the human, collects decisions, and sends them back into the same evaluator sessions — whose memory of their branch is intact — phrased as fixed constraints, not suggestions.

Three habits to steal from that exchange: the lead verifies before relaying (an evaluator’s plausible-but-wrong claim is the lead’s responsibility to catch); decisions are recorded durably the moment they’re made; and constraints flow back into agents that kept their context — nobody re-reads a branch from scratch.

Reconcile, don’t contaminate

The cross-ground phase has a subtle rule inherited from the research vault: isolation. Evaluators read each other’s drafts, but the drafts are copied inline into their instructions — branch A’s files never link to branch B’s. Whatever context a branch’s analysis needs from its sibling gets duplicated, not referenced. And the merged view — the one document that genuinely spans branches — lives outside all of them, which is exactly what Module 2’s gate enforces geometrically.

💡
Key insight: structure carries the discipline

Nobody has to remember the isolation rule under deadline pressure — the gate checks the synthesis’s location, the analysis notes’ links stay in-branch, and a violation blocks the run from finishing. Rules that matter get encoded where forgetting them is impossible.

And how does the gate know cross-grounding actually happened? It looks for the receipt — a formal analysis note in each branch. Here is that check, verbatim:

CODE — reorient/gates/reorient.mjs 

export function hasAnalysisNote(dir) {
  let entries = [];
  try { entries = readdirSync(dir).filter((f) => /^Analysis-.*\.md$/.test(f)); } catch { return false; }
  return entries.some((f) => {
    try { return /(^|\n)type:\s*analysis(\s|$)/.test(readFileSync(join(dir, f), "utf8")); } catch { return false; }
  });
}
PLAIN ENGLISH

A yes/no question: does this branch folder hold its analysis note?

Start with an empty list of candidates.

List the folder’s files and keep only ones named like “Analysis-something.md” — if the folder can’t even be read, the answer is no.

Now check whether at least one candidate…

…declares itself a formal analysis in its header (an unreadable file counts as no) —

…that one match is enough.

End of the check: a filename pattern AND a self-declaration, or the gate refuses to close the run.

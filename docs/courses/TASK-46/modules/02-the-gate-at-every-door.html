Module 2

The Gate at Every Door

One project living with these collisions every day — a game called promptworld, where several AI sessions routinely work the same repo — got tired of relying on every session’s memory and good manners. Its insight: each of the three failures from Module 1 has exactly one moment when it is still cheap to prevent. Miss the moment, and prevention turns into cleanup.

So promptworld built a single script — scripts/check-merge-drift.mjs, written under its spec 051 — and gave it three modes, one per moment. Think of a factory with a gate at every door: one at the entrance when your shift starts, one at each workbay before you open it, one at the shipping dock before anything leaves. Same guard, three posts.

Three modes, three moments

🌅

session

Run when a work session starts. It sweeps out leftover workspaces from already-merged tasks (the “janitor”), confirms your copy of main is current, and — the clever part — compares every open branch against every other, predicting which pairs will collide before anyone merges anything. That prediction table is called the drift matrix.

🔧

worktree

Run right before opening a new workspace for a task. It checks the root is sitting at the very freshest main (no stale checkouts), and — given a spec number you want to claim — checks nobody else took it, naming the next free number if they did. The silent collisions from Module 1, caught mechanically.

📦

pr

Run right before proposing your changes as a PR. It rehearses the merge in advance, predicting textual conflicts with main and with sibling branches, and warns about semantic overlaps — shared board files, documentation that pins the files you touched — that git alone would never mention.

Every run ends the same way: a single exit code, as unambiguous as a traffic light:

exit 0 Pass — the door opens, proceed.
exit 1 Blocked — the gate found real trouble (a predicted conflict, a taken spec number, a stale root). Fix it, re-run, and only proceed on 0.
exit 2 Environment error — the gate could not even perform the check (wrong directory, missing tooling). Not a verdict about your work: fix the setup, then re-run.
💡
Key insight: check where it’s preventable, not where it’s visible

A merge conflict becomes visible at merge time, but it becomes preventable much earlier — when the session starts, when the workspace opens, when the PR is about to exist. Putting the gate at those three doors converts days of cleanup into seconds of checking. Engineers call this general move “shift left”: move every check to the earliest moment it can possibly run.

The pattern, in a tool’s own words

The script lives in promptworld’s repo — but the clearest description of the pattern now lives somewhere more surprising: inside the praxisflux sweep skill, which learned to look for it (that’s Module 3’s story). Here is how the skill describes what a merge-drift gate is, verbatim:

SKILL — pdlc/skills/sweep/SKILL.md 

3. **Probe for a merge-drift gate** — hosts following the spec-051 pattern (promptworld)
   ship `scripts/check-merge-drift.mjs` with `session` / `worktree` / `pr` modes and
   0 pass / 1 blocked / 2 env-error exit codes. When present it is **mandatory at its
   choke points for the whole sweep**, not a runbook-author judgment call: run
   `node scripts/check-merge-drift.mjs session` now — it subsumes the fetch/ff-pull
   above, prescribes janitor cleanup of merged worktrees, and emits the n-way drift
   matrix Phase 1 needs. When absent, the raw git commands above stand.
PLAIN ENGLISH

Check whether this project follows the pattern promptworld pioneered in its spec 051…

…meaning it keeps a gate script at a known address, answering to the three mode names…

…and speaking the three-light language: 0 opens the door, 1 blocks it, 2 means the check itself could not run. If the script exists, obeying it is not optional…

…and not a matter of anyone’s judgment — so run the shift-start check immediately…

…it replaces the manual “refresh your copy of main” commands…

…tells you which leftover workspaces to sweep out, and produces the collision-prediction table…

…that the planning phase needs. And if the project has no such script? The old manual commands still apply — nothing is invented.

Good to know: why “pr” runs twice

Passing the shipping-dock gate once isn’t a lifetime pass. If you then rebase — replay your work on top of a newer main — you have effectively built a new shipment: same intent, different base. So the rule is mechanical: after every rebase, the pr gate runs again.

TASK-46 — The Gate at Every Door
Module 1

Many Robots, One Garage

Modern projects don’t have one AI session working at a time — they have several, in parallel, all editing the same repository. One session is building a feature, another is fixing a bug, a third is refreshing the docs. Picture several mechanics sharing one garage: each rolls the car onto their own lift, works on their own part — and then everyone’s changes have to fit back onto the same car.

Git makes the “own lift” part easy: each session works on its own branch, inside its own worktree. The trouble starts when the parallel work has to come back together. This module is about the three ways it goes wrong — and why two of the three are invisible until it’s too late.

Watch two sessions collide

Here are two well-behaved AI sessions, each doing exactly what it was asked, and the shared main branch caught in the middle. Neither session did anything wrong — and everything still goes wrong. Play the conversation:

A
Session A

Starting my task! I branched off main on Tuesday. Clean copy, all tests green.

B
Session B

Me too! I also need a number for my new spec folder. The highest one I can see is 051, so I’ll take 052.

A
Session A

Funny — the highest number I can see is also 051. Taking 052 for mine.

M
Main branch

Heads up: you have now BOTH created a folder called spec 052 — with completely different contents. I will happily accept both. No error. Good luck to whoever reads the specs later.

B
Session B

Done with my feature! Merging into main. Four files changed.

A
Session A

Wait. My branch suddenly conflicts with main in two files. I did not touch anything since yesterday!

M
Main branch

You did not move — I did. Your branch is based on Tuesday’s me. Session B just changed two of the files you also changed. The conflict was born the moment B merged; you are only discovering it now.

?

Three distinct failures hide in that exchange. A merge conflict: two sessions edited the same files, and the second one to arrive inherits the mess. A stolen spec number: both sessions claimed “052”, and because the folders have different names, git raises no error at all — the collision is silent. And a stale checkout: Session A was reasoning about Tuesday’s version of the project while the real one moved on without it.

⚠️
The nasty part: two of the three are silent

Git loudly flags a merge conflict — eventually. But it says nothing about two different spec folders sharing a number, and nothing about a branch quietly going stale while main moves. The failures you aren’t warned about are the ones that cost days.

The rules of the road (before this task)

The praxisflux sweep skill — the orchestrator that runs many tasks through development at once — already knew all of this. Its “concurrency doctrine” treats collisions as routine, not exceptional. Here are three of its actual rules:

SKILL — pdlc/skills/sweep/SKILL.md 

- On conflict: **rebase** (never merge-commit into a task branch), take main's side for
  anything you didn't deliberately change, then re-run gates — a rebase can silently
  invalidate a design-doc amendment or a pinned reference.
- Two PRs heavy in the same hotspot must not merge within one re-ground cycle without a
  rebase between them, or the grounding gates thrash.
- When your open PR conflicts with a sibling session's, let the **smaller** one merge
  first, regardless of whose it is.
PLAIN ENGLISH

When your work collides with main, replay your changes on top of the newest version — never mash the two histories together — and where you didn’t mean to differ, let main win…

…then re-run every check, because moving your work onto a new base can quietly break things that passed before…

…like a documentation note that was pinned to the old version and is now out of date.

Two batches of changes that hit the same busy files must not land back to back without…

…refreshing one against the other first — otherwise the documentation checks flip-flop endlessly.

And when your proposal collides with a teammate’s, the smaller one goes first…

…no matter whose it is — small changes are cheap to replay on top of big ones, not the reverse.

Good rules — but notice what they all have in common: they tell you what to do after you discover trouble, or they rely on the session remembering to check. Written doctrine only works if every session reads it, every time. The next module is about one project’s answer: stop relying on memory, and put a machine at the door.

Module 2

The Gate at Every Door

One project living with these collisions every day — a game called promptworld, where several AI sessions routinely work the same repo — got tired of relying on every session’s memory and good manners. Its insight: each of the three failures from Module 1 has exactly one moment when it is still cheap to prevent. Miss the moment, and prevention turns into cleanup.

So promptworld built a single script — scripts/check-merge-drift.mjs, written under its spec 051 — and gave it three modes, one per moment. Think of a factory with a gate at every door: one at the entrance when your shift starts, one at each workbay before you open it, one at the shipping dock before anything leaves. Same guard, three posts.

Three modes, three moments

🌅

session

Run when a work session starts. It sweeps out leftover workspaces from already-merged tasks (the “janitor”), confirms your copy of main is current, and — the clever part — compares every open branch against every other, predicting which pairs will collide before anyone merges anything. That prediction table is called the drift matrix.

🔧

worktree

Run right before opening a new workspace for a task. It checks the root is sitting at the very freshest main (no stale checkouts), and — given a spec number you want to claim — checks nobody else took it, naming the next free number if they did. The silent collisions from Module 1, caught mechanically.

📦

pr

Run right before proposing your changes as a PR. It rehearses the merge in advance, predicting textual conflicts with main and with sibling branches, and warns about semantic overlaps — shared board files, documentation that pins the files you touched — that git alone would never mention.

Every run ends the same way: a single exit code, as unambiguous as a traffic light:

exit 0 Pass — the door opens, proceed.
exit 1 Blocked — the gate found real trouble (a predicted conflict, a taken spec number, a stale root). Fix it, re-run, and only proceed on 0.
exit 2 Environment error — the gate could not even perform the check (wrong directory, missing tooling). Not a verdict about your work: fix the setup, then re-run.
💡
Key insight: check where it’s preventable, not where it’s visible

A merge conflict becomes visible at merge time, but it becomes preventable much earlier — when the session starts, when the workspace opens, when the PR is about to exist. Putting the gate at those three doors converts days of cleanup into seconds of checking. Engineers call this general move “shift left”: move every check to the earliest moment it can possibly run.

The pattern, in a tool’s own words

The script lives in promptworld’s repo — but the clearest description of the pattern now lives somewhere more surprising: inside the praxisflux sweep skill, which learned to look for it (that’s Module 3’s story). Here is how the skill describes what a merge-drift gate is, verbatim:

SKILL — pdlc/skills/sweep/SKILL.md 

3. **Probe for a merge-drift gate** — hosts following the spec-051 pattern (promptworld)
   ship `scripts/check-merge-drift.mjs` with `session` / `worktree` / `pr` modes and
   0 pass / 1 blocked / 2 env-error exit codes. When present it is **mandatory at its
   choke points for the whole sweep**, not a runbook-author judgment call: run
   `node scripts/check-merge-drift.mjs session` now — it subsumes the fetch/ff-pull
   above, prescribes janitor cleanup of merged worktrees, and emits the n-way drift
   matrix Phase 1 needs. When absent, the raw git commands above stand.
PLAIN ENGLISH

Check whether this project follows the pattern promptworld pioneered in its spec 051…

…meaning it keeps a gate script at a known address, answering to the three mode names…

…and speaking the three-light language: 0 opens the door, 1 blocks it, 2 means the check itself could not run. If the script exists, obeying it is not optional…

…and not a matter of anyone’s judgment — so run the shift-start check immediately…

…it replaces the manual “refresh your copy of main” commands…

…tells you which leftover workspaces to sweep out, and produces the collision-prediction table…

…that the planning phase needs. And if the project has no such script? The old manual commands still apply — nothing is invented.

Good to know: why “pr” runs twice

Passing the shipping-dock gate once isn’t a lifetime pass. If you then rebase — replay your work on top of a newer main — you have effectively built a new shipment: same intent, different base. So the rule is mechanical: after every rebase, the pr gate runs again.

Module 3

Teaching the Orchestrator

So promptworld had its gate. But here’s the problem TASK-46 was created to fix: the gate lived in one repo’s scripts and one repo’s docs. The sweep — the orchestrator skill from Module 1 that runs whole batches of tasks — knew the general rules of the road, but it would only use promptworld’s gate if a human (or a runbook author) remembered to say so. A safety practice that depends on someone remembering to mention it isn’t a practice yet. It’s a hope.

TASK-46’s move: teach the orchestrator itself to look for the gate. Think of a traveling foreman who, on arriving at any site, first checks whether the site posts its own safety officer at the door — and if it does, that officer’s word outranks the foreman’s habits, automatically. The change is small on paper — one skill file and one template, amended — and it flips who carries the responsibility: from every future session’s memory, to the tooling every session already runs.

One probe, three standing orders

The amended sweep now begins every run with a probe: does this project ship scripts/check-merge-drift.mjs? If yes, the skill’s own text declares the gate “mandatory at its choke points for the whole sweep, not a runbook-author judgment call” — and wires one invocation into each choke point:

1
At sweep start — session mode

Replaces the hand-typed “refresh main” commands, prescribes janitor cleanup of merged-and-forgotten workspaces, and hands its drift matrix to the planner — branch pairs predicted to collide are not allowed to develop in parallel lanes on the promise of an easy merge.

2
Before every new workspace — worktree mode

Must exit 0 before any git worktree add; with --spec NNN it also referees the spec-number race from Module 1, blocking a taken number and naming the next free one.

3
Before every PR, and again after every rebase — pr mode

The last gate before gh pr create. A nonzero exit blocks the PR outright, and the gate’s overlap warnings double as a checklist of companion artifacts the same PR must carry.

Here is the strongest of the three, verbatim from the amended skill:

SKILL — pdlc/skills/sweep/SKILL.md (Phase 2, step 7) 

7. Rebase onto fresh `origin/main`; re-run tests and gates AFTER the rebase (sibling
   merges change tripwires). With a merge-drift gate,
   `node scripts/check-merge-drift.mjs pr` from the worktree is the last gate before
   `gh pr create` — and again after every rebase; a nonzero exit blocks the PR, and its
   semantic-overlap warnings (board files, wiki-pinned sources, design surfaces) are the
   same-PR companion-artifact checklist. Then open the PR from the worktree.
PLAIN ENGLISH

Replay your finished work on top of the very latest shared version, then re-run every check — because a teammate’s merge may have changed what “passing” means…

…and if this project has a merge-drift gate…

…running its shipping-dock check is the final door before proposing your changes…

…and the door swings again after every rebase. Any answer other than “pass” stops the proposal cold…

…and the gate’s warnings about quieter overlaps — shared task-board files, documentation pinned to the files you touched, design references…

…are read as a to-do list: whatever they name must be updated in the same proposal. Only then does the PR open.

Written down, so nobody re-derives it

One last thread ties this to the sweep’s founding rule. A sweep outlives any single AI session, and the next session remembers nothing — it resumes from the runbook plus the task board alone. So the probe’s verdict can’t live in the session’s head: TASK-46 also amended the runbook template, adding a permanent line to its gates section:

TEMPLATE — pdlc/skills/sweep/templates/runbook.md 

- **Merge-drift gate: {{present at scripts/check-merge-drift.mjs | absent}}.** When
  present, mandatory at every choke point: `session` at sweep start (janitor + drift
  matrix), `worktree [--spec NNN]` before every `git worktree add`, `pr` from the
  worktree before every `gh pr create` AND after every rebase — nonzero exit blocks.
PLAIN ENGLISH

The runbook’s author fills in the blank: this project either has the gate at the standard address, or it doesn’t…

…and when it does, the three standing orders are spelled out right here — the shift-start check with its cleanup and collision forecast…

…the workspace check (with the spec number when one is being claimed) before every new workspace…

…and the shipping check before every proposal and after every rebase. Any session that later adopts this runbook obeys the gate without re-discovering it.

💡
Key insight: practices travel in tools, not in memos

Notice what TASK-46 did not do: it didn’t copy promptworld’s script into the plugin, and it didn’t write a memo urging sessions to please remember the gate. It gave the orchestrator a convention — a standard address, three mode names, three exit codes — and a standing order to obey whatever answers at that address. Any project, today or years from now, that ships a script honoring the convention gets the whole safety practice for free. That’s how good practices escape the repo they were born in.

Where this leaves things

The garage from Module 1 still has many robots in it — that part never changes. But the guard promptworld posted at three doors (Module 2) now travels with the orchestrator itself: any project that ships the convention gets the gates enforced automatically, and any project that doesn’t simply gets the old careful manual habits. Sweep skill v0.2.0, one probe, three standing orders — and one less thing that depends on anyone remembering.

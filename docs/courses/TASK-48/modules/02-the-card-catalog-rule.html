Module 2

The Card-Catalog Rule

Spec v2's first fix isn't a new format — it's a written rule for how readers behave

A good librarian never photocopies the encyclopedia. She checks the card catalog, walks to one shelf, pulls one volume, and opens it to one chapter. The building can hold a million books; your visit costs the same either way.

That behavior is what spec v2 writes into the contract. The single most important change of TASK-48 is a new section called "How consumers load a corpus" — a default loading discipline every reading tool is now expected to follow. The research behind this task was blunt: a format change that halves note size saves money once; a protocol change bounds cost forever, because the wiki can double while a task touching three concepts still loads three notes.

What the spec now says

The four rules, copied from the new section of docs/corpus-spec.md:

SPEC v2 (docs/corpus-spec.md) 

1. **`INDEX.md` first, always** — it is the routing surface.
2. **Notes just-in-time, individually** — route through the index (or the capsules, below)
   and load only the notes the task needs. Bulk-loading a corpus is never default behavior.
3. **Whole-corpus orientation reads `CAPSULES.md`**, not the note bodies.
4. **Within a note, `##` sections are the addressable unit** — a consumer that needs one
   aspect of a large note reads that section, not the file.
PLAIN ENGLISH

Always start with the table of contents — it exists to route you to the right note.

Then fetch notes one at a time, only as the task actually needs them —

— and never default to "just read everything," no matter how convenient it feels.

If your job genuinely is to survey the whole wiki, read the cheap summary file (next screen) instead of every full note.

And inside a big note, the section headings are valid stopping points — you may read just the one section you need —

— rather than the entire file, when one aspect is all the task calls for.

💡
Key insight: cost should scale with the task, not the library

The corpus grows linearly with the project — that's fine and unavoidable. The protocol's promise is that a session's cost grows only with what the session is trying to do.

Three sizes of the same knowledge

Rule 3 mentions a new file. Spec v2 formalizes a capsule tier: every note's one-line frontmatter description becomes its capsule — capped at 500 characters and written for routing ("what's inside, when to load it"), never as a teaser. A generated file, CAPSULES.md, collects every capsule in one place. The same knowledge now comes in three sizes:

🗂️

Index line

One line in INDEX.md. A couple dozen tokens — enough to decide "is this note even relevant?"

💊

Capsule

Up to 500 characters (~125 tokens) — what the note covers and when to load it. All capsules together: the whole wiki, ~10× cheaper than the full notes.

📖

Full note

The complete, provenance-pinned facts — loaded one at a time, only when the task needs that concept.

⚙️
CAPSULES.md is generated, never hand-written

The spec declares it derived state: producers regenerate it whenever any description changes, hand-editing it is an error, and it carries a header naming its generator and the exact commit it was generated at — so drift is detectable. It's also optional for readers: a wiki without one is still a valid corpus.

TASK-48 — Paying by the Page
Module 1

Paying by the Page

Why a knowledge base that grows with the project quietly makes every question more expensive

Imagine a reference library where you pay a photocopying fee for every page you pull. You walk in with one small question — "what time does the ferry leave?" — and the librarian, wanting to be thorough, photocopies the entire transportation encyclopedia and hands you the stack. You pay for all of it. Every visit. And the encyclopedia gets thicker every year.

That is roughly what was happening with this project's grounding wiki. AI sessions answering questions about the project would load tokens by the tens of thousands — often most of the wiki — to answer questions that touched three or four notes.

📏
The measured starting point

When this task began, the wiki held 26 notes totalling roughly 34,000 tokens. Loading "a few dozen pages" meant paying near-whole-corpus cost per session — and the corpus grows every time the project does.

⚠️
It's not just money — it's accuracy

Research this task drew on found that over-loading is a quality problem too: stuffing an AI's context window with irrelevant pages measurably degrades its answers. The expensive habit was also the worse-performing one.

The contract that said nothing about cost

Every wiki in this ecosystem follows one written contract — the corpus spec. Version 1 defined the shape precisely. Here is its entire layout rule:

SPEC v1 (docs/corpus-spec.md) 

<corpus-root>/
  INDEX.md          # required: one line per note — the recall surface
  <name>.md         # one note per concept; filename = frontmatter name + .md
  ...
PLAIN ENGLISH

A knowledge base is just a folder.

It must contain a table of contents — INDEX.md — with one line per note, so anything looking for a topic can find the right file.

Then one file per concept, named after the concept it covers.

…and that's the whole layout. Notice what's missing: not a word about how much of this a reader should load, or how big any note may grow.

Structure and provenance were contract; cost was habit. Nothing stopped a note from growing without bound, and nothing told a consumer "don't read everything." TASK-48's job was to close exactly that gap — by amending the contract, not by building new machinery.

Quick check

A project's wiki grows from 30 notes to 60 over a year. A teammate's AI session answers the same small question — "where is the deploy config?" — the old bulk-loading way, once at the start of the year and once at the end. What happens to the cost of that question?

Module 2

The Card-Catalog Rule

Spec v2's first fix isn't a new format — it's a written rule for how readers behave

A good librarian never photocopies the encyclopedia. She checks the card catalog, walks to one shelf, pulls one volume, and opens it to one chapter. The building can hold a million books; your visit costs the same either way.

That behavior is what spec v2 writes into the contract. The single most important change of TASK-48 is a new section called "How consumers load a corpus" — a default loading discipline every reading tool is now expected to follow. The research behind this task was blunt: a format change that halves note size saves money once; a protocol change bounds cost forever, because the wiki can double while a task touching three concepts still loads three notes.

What the spec now says

The four rules, copied from the new section of docs/corpus-spec.md:

SPEC v2 (docs/corpus-spec.md) 

1. **`INDEX.md` first, always** — it is the routing surface.
2. **Notes just-in-time, individually** — route through the index (or the capsules, below)
   and load only the notes the task needs. Bulk-loading a corpus is never default behavior.
3. **Whole-corpus orientation reads `CAPSULES.md`**, not the note bodies.
4. **Within a note, `##` sections are the addressable unit** — a consumer that needs one
   aspect of a large note reads that section, not the file.
PLAIN ENGLISH

Always start with the table of contents — it exists to route you to the right note.

Then fetch notes one at a time, only as the task actually needs them —

— and never default to "just read everything," no matter how convenient it feels.

If your job genuinely is to survey the whole wiki, read the cheap summary file (next screen) instead of every full note.

And inside a big note, the section headings are valid stopping points — you may read just the one section you need —

— rather than the entire file, when one aspect is all the task calls for.

💡
Key insight: cost should scale with the task, not the library

The corpus grows linearly with the project — that's fine and unavoidable. The protocol's promise is that a session's cost grows only with what the session is trying to do.

Three sizes of the same knowledge

Rule 3 mentions a new file. Spec v2 formalizes a capsule tier: every note's one-line frontmatter description becomes its capsule — capped at 500 characters and written for routing ("what's inside, when to load it"), never as a teaser. A generated file, CAPSULES.md, collects every capsule in one place. The same knowledge now comes in three sizes:

🗂️

Index line

One line in INDEX.md. A couple dozen tokens — enough to decide "is this note even relevant?"

💊

Capsule

Up to 500 characters (~125 tokens) — what the note covers and when to load it. All capsules together: the whole wiki, ~10× cheaper than the full notes.

📖

Full note

The complete, provenance-pinned facts — loaded one at a time, only when the task needs that concept.

⚙️
CAPSULES.md is generated, never hand-written

The spec declares it derived state: producers regenerate it whenever any description changes, hand-editing it is an error, and it carries a header naming its generator and the exact commit it was generated at — so drift is detectable. It's also optional for readers: a wiki without one is still a valid corpus.

Module 3

The Overstuffed Note

A size budget, a splitting rule borrowed from Wikipedia — and a counter-rule that stops the budget from doing harm

A filing cabinet works because no folder is allowed to become a box. When one folder starts bulging, an organized person doesn't cram harder — they split its contents into labeled sub-folders and leave a note in the original saying where everything went.

Wikis have the same failure mode: growth concentrates in a few hot pages. In this project's wiki, the largest note had already grown to about 2.4× the average. Left alone, "just add it to the existing note" always wins — and the just-in-time protocol from Module 2 stops paying off, because even one note becomes a heavy read.

What the spec now says

Spec v2 adds a hard budget, and — just as important — a rule about when not to act on it. Copied from docs/corpus-spec.md:

SPEC v2 (docs/corpus-spec.md) 

A note body (everything below the frontmatter) must stay at or under **8,000 characters**
(~2k tokens). The budget binds producers at write/update time; readers never reject an
over-budget note.
**Minimum-content counter-rule:** never split when the child would hold less than ~1,500
characters of substance, or would merely duplicate the summary left behind. An over-cap
parent with nothing splittable is acceptable — flag it, don't butcher it.
PLAIN ENGLISH

No note's content may grow past about 8,000 characters — roughly 2,000 tokens, a comfortable single read.

The rule binds whoever WRITES the note, at writing time. Readers never refuse an oversized note —

— an over-budget note is a producer's problem to fix, never a reader's reason to fail.

But there's a floor as well as a ceiling: never carve out a child note that would hold less than about 1,500 characters of real substance —

— or one that would just restate the summary you'd leave behind in the parent.

If a big note has nothing genuinely splittable, leaving it over budget is the correct call: mark it, don't mangle it.

📚
Borrowed from a 20-year precedent

This is Wikipedia's "summary style" discipline, imported: absorb growth by adding depth (child pages), not by inflating pages — with an explicit threshold and a minimum-content rule so nobody splits a page into useless stubs.

Anatomy of a summary-style split

When a note hits the cap and genuinely has subtopics, the split follows four steps:

1
Move the subtopic out

The bulging section's content becomes a new child note — one concept per note, as always.

2
Leave a summary behind

The parent keeps a one-paragraph summary of the child plus a wikilink to it — the reader still gets the gist without leaving the page.

3
Link back

The child links to its parent, so neither direction dead-ends.

4
Register the child

INDEX.md gains one line for the new note — the card catalog stays complete.

And because Module 2 made every note's description a routed-to capsule, spec v2 closes the loop on honesty: capsules are drift surfaces. A note edit that changes what the note covers must update its capsule in the same pass — the same re-verify discipline the wiki already applies to its provenance pins.

What TASK-48 deliberately did not do

This task changed one prose file — the contract. Everything mechanical was left to its successors, and two whole approaches were rejected outright by the research:

⏭️

Deferred, on purpose

Enforcement tooling (gate checks, the CAPSULES.md generator), reworking the existing wiki to conform, and updating consumer tools — each is its own follow-up task. Spec first, machinery second.

🚫

Rejected, with reasons

Search-engine-style retrieval infrastructure (earns its keep only on far larger corpora) and load-time text compression (the wiki is read by humans too, and its plain Markdown is the very artifact the gates pin).

🤝
The compatibility promise

Every v1 wiki remains readable under v2. The new file is optional for readers; the new budgets bind producers when they write or update. Nothing that consumed a corpus yesterday breaks today — the contract grew, it didn't turn.

TASK-47 — First Commit Wins
Module 1

The Race Nobody Wins

Why "check before you claim" quietly fails the moment two sessions do it at once

Picture two travel agents on the phone with two different customers. Both open the hotel's booking system, both see Room 12 sitting empty, and both tell their customer "you're all set." Neither one did anything wrong — they just both looked at the shared booking ledger a half-second before the other one wrote to it.

This is exactly what happened to two AI coding sessions working the same project. Both were about to start a new piece of work. Both checked the project's task list for a free spec number, both saw "065" was open, and both started writing spec 065 — at the same time.

⚠️
This actually happened

This is the real incident that produced TASK-47: two concurrent sessions in a companion project raced on the same task and the same spec number, because the project's own playbook only told them to check first — never to claim.

💡
Key insight: checking is not claiming

Computer scientists call this a race condition, and this specific flavor has a name: time-of-check to time-of-use. The gap between "I looked and it was free" and "I actually took it" is where two sessions can both walk through the same open door at once.

The doctrine that let it happen

Before this task, the sweep runbook template — the instructions every orchestrating session reads before touching the board — carried exactly one line about this:

OLD RUNBOOK TEXT 

- Spec-number collisions: check `origin/main:specs/` before claiming an NNN.
PLAIN ENGLISH

Look at the shared folder before you pick a number — but "look" is the whole instruction. It never says what to do the moment two sessions look at the same instant.

"Check before claiming" describes the failure mode instead of preventing it — it's the equivalent of telling both travel agents "make sure to look at the ledger first." They did. That's exactly how the collision happened.

Module 2

First Commit Wins

How the new doctrine turns "look before you leap" into an actual, unambiguous claim

A community garden doesn't hand out plots by trusting people to just notice an empty patch of dirt and start planting. It has two steps: you sign your name in the logbook at the shed, and you hammer a labeled stake into the actual ground. Either one alone is weak — a name in a book nobody re-checks, or a stake someone could miss. Together, anyone walking by can tell in five seconds whether a plot is taken.

TASK-47 gives the sweep runbook template that same two-part claim, and moves it to the earliest possible moment: the first commit of any task.

What the runbook now says

This is the replacement bullet, copied exactly from pdlc/skills/sweep/templates/runbook.md:

CODE (runbook.md) 

- **Claim before work:** the FIRST commit of any task claims it — board card →
  In Progress AND the spec number's directory (a stub claims the number) — before any
  spec authoring or code. Push immediately (`git push -u origin <branch>` on first
  commit, so in-flight work is auditable from any clone); never force-push a claim.
PLAIN ENGLISH

The very first commit you make on a task IS the claim — not a side-note, the commit itself.

Two things flip together: the board card moves to "In Progress," and a folder for the spec number gets created (even just a placeholder file).

Both of those happen before you write a single line of the actual spec or code — claim first, work second, never the other order.

Then push that commit to the shared remote right away, and never overwrite someone else's history to "fix" your claim — a forced push would erase the very race-detection this doctrine depends on.

💡
Key insight: the claim IS the commit

There's no separate "reservation" step to forget or skip. The same commit that starts the work also stakes it — so there's nothing to do differently, just an order to respect: claim, then build.

Why never force-push the claim

A force-push rewrites the shared history instead of adding to it. If your claim collided with someone else's, force-pushing wouldn't resolve the race — it would erase the evidence that a race happened at all, and silently delete their claim underneath them.

🚫
The rule exists because of what it protects

The whole doctrine depends on the shared remote being an honest record of who claimed what, and when. Force-pushing over someone else's claim breaks that record — which is exactly the failure this doctrine was built to prevent.

Quick check

You've just made your first commit on a new task: the board card flipped to In Progress and you added a stub file for spec number 072. You get pulled away before pushing. Is the claim actually in effect yet?

Module 3

When the Push Bounces

A rejected push isn't a glitch to work around — it's the doctrine working exactly as designed

An electronic door badge reader only opens for the first valid badge it sees in a given instant. If two people swipe within the same fraction of a second, one door opens and the other reader flashes red. That red light isn't a malfunction — it's the system telling the second person, unambiguously, "someone already went through."

A rejected git push after a claim attempt is that red light. It means someone else's claim reached the shared remote first.

What the runbook now says

CODE (runbook.md) 

- **A rejected push means you lost the race:** fetch, re-read the board and `specs/`.
  If another session now holds that task or number, STOP the lane and surface it to
  the operator. Unrelated rejection (e.g. a board-notes push) with the task+number
  still free → rebase and re-push the claim.
PLAIN ENGLISH

Don't panic and don't retry blindly — first, pull the latest state of both the board and the specs folder so you're looking at current reality, not your stale snapshot of it.

If that fresh look shows someone else genuinely holds your task or your spec number now, the race is over and you lost it — stop that entire branch of work and tell the human operator, rather than plowing ahead.

But if the rejection turns out to be for an unrelated reason (say, someone else pushed an unrelated board-notes commit) and your task and number are still free —

— then it's safe to just rebase onto the latest remote state and push your claim again.

The decision, step by step

Every rejected push runs through the same short checklist before you do anything else:

1
Fetch — get the current truth

Pull the latest remote state instead of guessing why the push failed.

2
Re-read the board and specs/

Check whether your task or your spec number now belongs to someone else.

3
Contended? Stop and surface it

Someone else's claim landed first — halt this lane of work and hand the situation to the operator instead of improvising.

4
Not contended? Rebase and re-push

The rejection was for an unrelated reason — your claim is still safe to make; just replay it on top of the newer history.

When a project can check this automatically

Some host projects ship a merge-drift gate. For those, the runbook now names the exact commands that make this doctrine mechanical instead of a matter of discipline:

🔒

claim --dir NNN-slug

Run before creating any new spec folder — blocks automatically if that number is already taken, instead of trusting a manual folder-listing check.

🌳

worktree --spec NNN --task TASK-<n>

Run before cutting a worktree — warns if the board card isn't actually claimed yet, and accepts a spec dir claim already made by that same task.

ℹ️
Discipline where there's no gate, mechanics where there is

Not every project that uses this runbook template ships a merge-drift gate. The claim-before-work doctrine works either way — as a human/AI discipline everywhere, and as an enforced, unmissable check wherever the mechanics exist.

TASK-49 — The Summary Shelf Gets Built
Module 1

Building the Summary Binder

The previous task wrote the rule; this task built the machine that keeps the rule true

TASK-48 amended this project's knowledge-base contract: every wiki should offer a cheap summary file, CAPSULES.md — one short blurb per note, so a reader who needs the whole picture can skim the binder instead of photocopying every book. The contract also set two size limits: each blurb stays under 500 characters, each note body under 8,000.

But a contract with no machinery is a wish. Nothing generated the binder, and nothing checked the limits. TASK-49 built both halves: a generator that produces CAPSULES.md mechanically, and new checks inside the project's existing gate so the limits are enforced rather than remembered.

🗜️
Derived state, never hand-written

CAPSULES.md is like the index of a book: you never edit the index by hand and hope the page numbers stay right — you regenerate it from the book. The spec calls this derived state; hand-editing it is defined as an error.

What the generated file looks like

The generator (grounding-wiki/scripts/capsules.mjs) reads the wiki's table of contents and every note, then writes this — always in the same order, always byte-identical for the same input:

CAPSULES.md (generated) 

# Capsules — the corpus rollup
Generated by grounding-wiki scripts/capsules.mjs at corpus commit 46128dc…
- [[overview]] — what praxisflux is: a plugin marketplace on a shared chassis
  What the note covers and when to load it — its full 500-character-max capsule.
- [[gate-runner]] — the Stop-hook harness: resolves roots, runs gate fns
  The next capsule, and so on — one pair of lines per note, in index order.
PLAIN ENGLISH

A title announcing what this file is: the summary binder.

A stamped header naming which program wrote the file and the exact project snapshot it was written at — so anyone can later detect whether the binder has fallen behind the notes.

Then, for each note: first its one-liner copied straight from the table of contents…

…followed by its capsule — the short "what is in this note and when should you open it" blurb from the note itself.

The next note gets the same two-line treatment…

…all the way down, in exactly the order the table of contents lists them. Same wiki in, same binder out, every single time.

🔁
Why "byte-identical" matters

Because the output is perfectly predictable, a checker can regenerate the file in memory and compare it to what is on disk. Any difference — a note edited without refreshing the binder, or someone hand-tweaking it — is caught mechanically. Module 2 shows that trick in action.

Module 2

The Gate Grows Teeth

Size limits that live in a checker can't be forgotten — three new failure conditions in the freshness gate

This project already had a freshness gate: an automated check that fails whenever a wiki note's underlying code changed after the note was last verified. It runs before every commit, before every push, and in CI. TASK-49 taught that same gate the new size rules, so the token budgets stop being a habit and become a checkpoint.

💊

Capsule too long

A note's blurb over 500 characters fails, naming the note and exactly how far over it is.

📚

Note too big

A body over 8,000 characters fails, pointing at the spec's split rule — break the note into summary-plus-children.

🗂️

Binder out of date

A CAPSULES.md that no longer matches a fresh regeneration — stale or hand-edited — fails, naming the exact command that fixes it.

The checks, in miniature

The heart of the enforcement, simplified from grounding-wiki/gates/capsules.mjs:

gates/capsules.mjs (simplified) 

const adopted = existsSync(join(dir, "CAPSULES.md"));
if (desc.length > CAPSULE_BUDGET) fail("over the 500-char capsule budget");
if (body.length > NOTE_BODY_BUDGET)
  exempt ? warn(reason) : fail("split summary-style");
if (renderCapsules(commitFromHeader) !== existing)
  fail("stale — regenerate: node scripts/capsules.mjs");
PLAIN ENGLISH

First, look whether this wiki has a summary binder at all — that single fact decides how strict everything below will be (Module 3 explains why).

Measure every blurb: longer than 500 characters means the check fails and the message names the guilty note and the overage.

Measure every note body against the 8,000-character cap…

…but a note formally marked "exempt, here is why" only draws a warning — the spec accepts that some notes genuinely cannot be split, it just insists the exception be declared, not silent.

Finally, rebuild the binder in memory — at the very project snapshot its header claims — and compare it to the file on disk…

…any mismatch fails, and the error message contains the exact command that regenerates it. Every failure names its own fix.

🔍
The regenerate-and-compare trick

This is why Module 1 insisted on byte-identical output. The checker never "reads" the binder for meaning — it simply rebuilds it and compares bytes. Stale content, a missing note, a hand-edit: all become the same detectable thing, a difference.

Module 3

The Adoption Switch

How to turn on strict enforcement without breaking every wiki that predates the rule

Here is the trap TASK-49 had to avoid. The moment the gate starts failing oversized notes, every wiki written before the rule existed — including this very project's own wiki, which has one note at 11,742 characters — would go red. Builds would block on work that hasn't been scheduled yet. The classic migration problem: you want the new law enforced, but you can't arrest everyone retroactively.

The solution: enforcement is keyed on adoption, and the adoption signal is simply whether the wiki has a CAPSULES.md. No new setting, no config file — the artifact the spec already defines doubles as the switch.

🔔

No binder yet: warnings

The same checks run, but only as notices — visibility during adoption, nothing blocks. Legacy wikis stay green.

🚨

Binder present: failures

Generating CAPSULES.md is opting in. From then on, over-budget capsules and bodies, and a stale binder, block the gate.

This repo, today: warned but green

This project's own wiki hasn't adopted yet — that conversion is the next task, TASK-50. So its gate output today looks like this:

gate output on this repo (today) 

warn: v2 budget (warn-only until this corpus adopts CAPSULES.md):
  docs/wiki/build-and-release.md: body is 11742 chars — 3742 over
  the 8000-char note budget; split summary-style, or add
  size_budget_exempt if nothing is splittable
wiki-freshness ok: 25 notes fresh against their pinned sources
PLAIN ENGLISH

"Heads up — this wiki hasn't switched the strict rules on yet, so what follows is advice, not a blockade."

One note is 11,742 characters — 3,742 over the cap. The exact debt TASK-50 will pay down is already measured and named.

And the fix is spelled out: split the note summary-style…

…or, if it genuinely can't be split, declare a formal exemption.

Meanwhile the gate still passes: everything else about the wiki is fresh and verified. Warned, but green — exactly the migration posture.

🎯
Why this ordering is deliberate

TASK-49 ships the machinery with the safety on. TASK-50 will trim the oversized descriptions, split the fat note, and generate this wiki's real CAPSULES.md — and the moment that file lands, the very machinery built here starts holding the line for good.

How you know it works

None of this shipped on trust. The task added a dedicated test file that builds throwaway wikis and proves every behavior: the generator writes byte-identical output with the right header and index order; an adopted wiki fails on an oversized capsule, an oversized body, and a hand-edited binder; a declared exemption downgrades to a warning; an unadopted wiki only warns; and the gate's original duties are untouched. The full suite — 167 tests — runs before every commit to this repository.

Because the gate and the two wiki skills changed behavior, the plugin's skills were version-bumped and the whole marketplace released as 0.14.0 — with the project's own wiki notes re-verified and re-pinned against the change, per the project's rule that documentation claims must always name the exact code version they were checked against.

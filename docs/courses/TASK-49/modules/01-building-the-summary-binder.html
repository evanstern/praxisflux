Module 1

Building the Summary Binder

The previous task wrote the rule; this task built the machine that keeps the rule true

TASK-48 amended this project's knowledge-base contract: every wiki should offer a cheap summary file, CAPSULES.md — one short blurb per note, so a reader who needs the whole picture can skim the binder instead of photocopying every book. The contract also set two size limits: each blurb stays under 500 characters, each note body under 8,000.

But a contract with no machinery is a wish. Nothing generated the binder, and nothing checked the limits. TASK-49 built both halves: a generator that produces CAPSULES.md mechanically, and new checks inside the project's existing gate so the limits are enforced rather than remembered.

🗜️
Derived state, never hand-written

CAPSULES.md is like the index of a book: you never edit the index by hand and hope the page numbers stay right — you regenerate it from the book. The spec calls this derived state; hand-editing it is defined as an error.

What the generated file looks like

The generator (grounding-wiki/scripts/capsules.mjs) reads the wiki's table of contents and every note, then writes this — always in the same order, always byte-identical for the same input:

CAPSULES.md (generated) 

# Capsules — the corpus rollup
Generated by grounding-wiki scripts/capsules.mjs at corpus commit 46128dc…
- [[overview]] — what praxisflux is: a plugin marketplace on a shared chassis
  What the note covers and when to load it — its full 500-character-max capsule.
- [[gate-runner]] — the Stop-hook harness: resolves roots, runs gate fns
  The next capsule, and so on — one pair of lines per note, in index order.
PLAIN ENGLISH

A title announcing what this file is: the summary binder.

A stamped header naming which program wrote the file and the exact project snapshot it was written at — so anyone can later detect whether the binder has fallen behind the notes.

Then, for each note: first its one-liner copied straight from the table of contents…

…followed by its capsule — the short "what is in this note and when should you open it" blurb from the note itself.

The next note gets the same two-line treatment…

…all the way down, in exactly the order the table of contents lists them. Same wiki in, same binder out, every single time.

🔁
Why "byte-identical" matters

Because the output is perfectly predictable, a checker can regenerate the file in memory and compare it to what is on disk. Any difference — a note edited without refreshing the binder, or someone hand-tweaking it — is caught mechanically. Module 2 shows that trick in action.

Regeneration becomes part of the routine

A generator nobody runs is as useless as a rule nobody checks. So the two wiki skills — the instructions AI sessions follow when they build or refresh a wiki — now make regeneration a standard step. Here is how a wiki-refresh session ends today:

✓

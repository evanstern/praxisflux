TASK-41 — The Last Mandatory Course
Module 1

A Rule the Artifacts Outgrew

This project had a rule: every finished task must leave behind an interactive course — a little teaching website like the one you are reading right now. A lovely idea. This course is about how that rule died, and what replaced it. Yes: you are reading a course about the decision to stop requiring courses. It is the last one that was mandatory.

Think of a diary that solemnly promises “an entry every single day.” For the first week, it delivers. Then life speeds up, entries get skipped — but the promise on page one stays. The diary now lies. In this project, a lying document is the one unforgivable thing.

The promise, as written

Here is the actual opening of the old rulebook — docs/task-courses.md as it stood before this task. Read the very first word:

DOC — docs/task-courses.md (before TASK-41) 

Every completed task (generally 1:1 with a merged PR) leaves behind a small interactive
course at `docs/courses/TASK-XX/`, built with the codebase-to-course chrome and scoped to
**just that task's work**: the question it answered, what was built, what was learned. The
pattern is borrowed from the-stacks, where it is already standing practice.
PLAIN ENGLISH

EVERY finished task — no exceptions — must leave behind a small teaching website…

…stored in a folder named after the task, and built with the standard course toolkit…

…covering only what that one task did: the question, the work, the lessons.

We copied this habit from another project where it was already routine.

“Every completed task.” Strong words. Now let’s check them against reality — this project has a habit of doing exactly that, because one of its founding principles is that a claim is only worth the artifacts behind it.

💡
Docs drift toward fiction unless something pushes back

Engineers call this documentation drift: the code and the docs describing it slowly diverge, because changing reality never automatically changes the text about it. Mature projects treat a doc’s claims like a promise that must be either enforced or withdrawn — never left quietly false.

Why weaken the rule instead of enforcing it?

“Just follow the rule harder” was on the table. Three facts killed it:

🏋️

Heaviest ceremony

~2MB of generated HTML per course — the most expensive ritual in the methodology, demanded even for tiny tasks.

📉

~10 of 66 complied

When 85% of cases ignore a rule, the rule is not being broken — it is being voted out by the people doing the work.

🦴

Courses fossilize

Old courses fail their own quality check whenever the course toolkit upgrades — a problem Module 3 unpacks.

So the project owner decided: courses become opt-in. Not deleted, not disgraced — just no longer demanded for every task. Module 2 shows the mechanism that replaced the mandate.

Module 2

One Choice, Made Once

What replaces a mandate? The lazy answer is “ask every time” — and it was explicitly rejected. Asking “want a course for this one?” at the end of every task just converts a heavy ritual into a nagging one. Instead, each project makes a standing choice: decide once, write it down, never get asked again.

It works like a coffee subscription, not a coffee counter. You do not re-answer “beans or ground? how often?” with every delivery — you set a preference once, and every future delivery consults it. Change your mind? Edit the preference, deliberately, once.

Three grains to choose from

A project picks exactly one of three settings — the grain at which teaching artifacts get made:

🔬

per-task

The old rule, now voluntary: every completed task ships a course in a folder named for the task. Maximum coverage, maximum cost.

📦

per-feature

One course per shipped feature — a whole epic or delivery, named for the feature. Individual tasks ship nothing.

🚫

none

No courses at all. The board, the wiki, and git history remain the record. A legitimate choice, honestly stated.

And the choice must live somewhere durable — a written artifact, not a memory. For most projects that is a courses: line in the project’s planted grounding block. For this repository itself, it is a “Course policy” stanza in docs/task-courses.md plus a matching line in the repo’s CLAUDE.md workflow.

ℹ️
Configuration over interrogation

This is a classic engineering pattern: replace a repeated runtime question with a declared setting read from config. It kills decision fatigue, makes behavior predictable, and — because the setting is a committed file — leaves a paper trail when it changes.

Module 3

Snapshots, Not Living Docs

One question remained: when a course gets old, must someone maintain it? This project already keeps a set of documents eternally fresh — its wiki notes are pinned to code versions and automatically flagged the moment the code moves on. Should courses live under the same regime?

TASK-41’s answer: no. A course is a photograph, not a mirror. A photo of your street in 2019 is not “wrong” because a bakery closed — it is a true record of 2019. Demanding it stay current would mean re-shooting every photo forever. Courses are declared snapshot-exempt: checked once when built, never re-checked after.

Why exempt them? Because of this code

The pressure was real, not hypothetical. Every course is checked by a gate, and part of that gate inspects the chrome — the shared toolkit files inside the course folder. Here is the actual check, verbatim from validate.mjs:

CODE — codebase-to-course/skills/codebase-to-course/references/validate.mjs 

const STAMP = /chrome v(\d+)/;
export function checkChrome(courseDir) {
  const fails = [];
  for (const f of ["styles.css", "main.js"]) {
    const p = join(courseDir, f);
    if (!existsSync(p)) { fails.push(`${f}: missing from ${courseDir}`); continue; }
    const m = STAMP.exec(readFileSync(p, "utf8").slice(0, 600));
    if (!m) fails.push(`${f} has no chrome version stamp — that's v1, the retired side-by-side renderer. Upgrade: copy the plugin references/ files over this course dir and rebuild (gotchas.md "Stale Chrome").`);
    else if (+m[1] !== CHROME_VERSION) fails.push(`${f} is chrome v${m[1]} but this validator is v${CHROME_VERSION} — mixed chrome. Re-copy ALL reference files together, then rebuild.`);
  }
  return fails;
}
PLAIN ENGLISH

Define the pattern to hunt for: a “model year” stamp like “chrome v2”.

This is the inspection: hand it a course folder and it reports problems.

Start with an empty list of complaints.

Inspect the two shared toolkit files every course carries: its stylesheet and its engine script.

Work out where that file should sit inside this course folder.

If the file is missing entirely, complain and move on to the next one.

Otherwise read the top of the file and look for the model-year stamp.

No stamp at all? That is the retired first generation — complain, and explain how to upgrade.

Stamp present but the wrong number? Mixed generations — complain about that too.

Close the loop over both files.

Hand back the list of complaints; an empty list means the chrome passes.

…and that is the whole inspection.

See the trap? The stamp is compared against the current generation. The day the toolkit bumps from v2 to v3, every course ever built fails this check — including the one you are reading. Nothing about their content changed; the world moved. That is a fossil, not a failure.

Two kinds of documents, two contracts

The policy draws one clean line, based on what each document claims:

🪞
Wiki notes — mirrors — must stay fresh

They claim “this is how the code is now.” That claim rots the moment code changes, so every note is re-verified and re-pinned when its sources move.

📸
Courses — photographs — are snapshot-exempt

They claim “this is what one unit of work was.” A claim about the past cannot go stale. The gate applies once, at build time, and never again.

💡
Match the maintenance contract to the claim

This is a deep documentation principle: a doc describing the present needs machinery to keep it true; a doc describing the past only needs to be kept intact. Forcing past-tense records through present-tense freshness checks is ceremony without a consumer — work nobody benefits from.

The same honesty applies to history. Courses exist for only a subset of Done tasks — the ones built while the old mandate was in force. The new policy does not retroactively demand the missing ones, and it does not delete the existing ones. They stand as what they are: snapshots of the mandate era. And this course — docs/courses/TASK-41/, documenting the policy change itself — is the last one built because a rule said so.

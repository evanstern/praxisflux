Module 3

Snapshots, Not Living Docs

One question remained: when a course gets old, must someone maintain it? This project already keeps a set of documents eternally fresh — its wiki notes are pinned to code versions and automatically flagged the moment the code moves on. Should courses live under the same regime?

TASK-41’s answer: no. A course is a photograph, not a mirror. A photo of your street in 2019 is not “wrong” because a bakery closed — it is a true record of 2019. Demanding it stay current would mean re-shooting every photo forever. Courses are declared snapshot-exempt: checked once when built, never re-checked after.

Why exempt them? Because of this code

The pressure was real, not hypothetical. Every course is checked by a gate, and part of that gate inspects the chrome — the shared toolkit files inside the course folder. Here is the actual check, verbatim from validate.mjs:

CODE — codebase-to-course/skills/codebase-to-course/references/validate.mjs 

const STAMP = /chrome v(\d+)/;
export function checkChrome(courseDir) {
  const fails = [];
  for (const f of ["styles.css", "main.js"]) {
    const p = join(courseDir, f);
    if (!existsSync(p)) { fails.push(`${f}: missing from ${courseDir}`); continue; }
    const m = STAMP.exec(readFileSync(p, "utf8").slice(0, 600));
    if (!m) fails.push(`${f} has no chrome version stamp — that's v1, the retired side-by-side renderer. Upgrade: copy the plugin references/ files over this course dir and rebuild (gotchas.md "Stale Chrome").`);
    else if (+m[1] !== CHROME_VERSION) fails.push(`${f} is chrome v${m[1]} but this validator is v${CHROME_VERSION} — mixed chrome. Re-copy ALL reference files together, then rebuild.`);
  }
  return fails;
}
PLAIN ENGLISH

Define the pattern to hunt for: a “model year” stamp like “chrome v2”.

This is the inspection: hand it a course folder and it reports problems.

Start with an empty list of complaints.

Inspect the two shared toolkit files every course carries: its stylesheet and its engine script.

Work out where that file should sit inside this course folder.

If the file is missing entirely, complain and move on to the next one.

Otherwise read the top of the file and look for the model-year stamp.

No stamp at all? That is the retired first generation — complain, and explain how to upgrade.

Stamp present but the wrong number? Mixed generations — complain about that too.

Close the loop over both files.

Hand back the list of complaints; an empty list means the chrome passes.

…and that is the whole inspection.

See the trap? The stamp is compared against the current generation. The day the toolkit bumps from v2 to v3, every course ever built fails this check — including the one you are reading. Nothing about their content changed; the world moved. That is a fossil, not a failure.

Two kinds of documents, two contracts

The policy draws one clean line, based on what each document claims:

🪞
Wiki notes — mirrors — must stay fresh

They claim “this is how the code is now.” That claim rots the moment code changes, so every note is re-verified and re-pinned when its sources move.

📸
Courses — photographs — are snapshot-exempt

They claim “this is what one unit of work was.” A claim about the past cannot go stale. The gate applies once, at build time, and never again.

💡
Match the maintenance contract to the claim

This is a deep documentation principle: a doc describing the present needs machinery to keep it true; a doc describing the past only needs to be kept intact. Forcing past-tense records through present-tense freshness checks is ceremony without a consumer — work nobody benefits from.

The same honesty applies to history. Courses exist for only a subset of Done tasks — the ones built while the old mandate was in force. The new policy does not retroactively demand the missing ones, and it does not delete the existing ones. They stand as what they are: snapshots of the mandate era. And this course — docs/courses/TASK-41/, documenting the policy change itself — is the last one built because a rule said so.

Module 2

One Choice, Made Once

What replaces a mandate? The lazy answer is “ask every time” — and it was explicitly rejected. Asking “want a course for this one?” at the end of every task just converts a heavy ritual into a nagging one. Instead, each project makes a standing choice: decide once, write it down, never get asked again.

It works like a coffee subscription, not a coffee counter. You do not re-answer “beans or ground? how often?” with every delivery — you set a preference once, and every future delivery consults it. Change your mind? Edit the preference, deliberately, once.

Three grains to choose from

A project picks exactly one of three settings — the grain at which teaching artifacts get made:

🔬

per-task

The old rule, now voluntary: every completed task ships a course in a folder named for the task. Maximum coverage, maximum cost.

📦

per-feature

One course per shipped feature — a whole epic or delivery, named for the feature. Individual tasks ship nothing.

🚫

none

No courses at all. The board, the wiki, and git history remain the record. A legitimate choice, honestly stated.

And the choice must live somewhere durable — a written artifact, not a memory. For most projects that is a courses: line in the project’s planted grounding block. For this repository itself, it is a “Course policy” stanza in docs/task-courses.md plus a matching line in the repo’s CLAUDE.md workflow.

ℹ️
Configuration over interrogation

This is a classic engineering pattern: replace a repeated runtime question with a declared setting read from config. It kills decision fatigue, makes behavior predictable, and — because the setting is a committed file — leaves a paper trail when it changes.

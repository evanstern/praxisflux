Module 2

One Note, Split Summary-Style

The 11,742-character note becomes a hub and two children — nothing deleted, everything findable

The oversized note, build-and-release.md, described the project's entire build-and-release story in one file: packaging, catalogs, version rules, CI, publishing, and the surface other projects consume. The wiki contract's fix is called a summary-style split: move coherent subtopics into new child notes, and leave a short summary plus a link where each one used to be.

The judgment call is the word coherent. You split by subject, not by arithmetic — and the contract forbids children with less than about 1,500 characters of real substance, so you can't hit the number by scattering confetti. Two natural children emerged:

🚀

release-pipeline

The merge-to-main mechanics: the version-bump rule on changed code, the checks every proposal runs, and the publish-then-tag ordering that makes releases safe to automate.

📦

gates-consumption-surface

How other projects run this project's checks: the installable package, the plug-in CI action, and the exit-code contract they share.

The parent kept everything else — packaging, catalog, version sync — plus one summary paragraph and a link per child. Each child links back. The wiki's table of contents gained exactly two lines, added without rearranging anything that existed. After the split: parent 7,635 characters, children 4,437 and 3,494. All under the cap, each child well over the substance floor.

A child note is born with its own passport

In this wiki, every note must prove itself: it lists the code files it describes and the exact project snapshot its claims were last checked against. A child can't inherit the parent's paperwork — it gets its own, listing only its files:

release-pipeline.md — the header (abridged) 

name: release-pipeline
kind: pipeline
sources:
  - .github/workflows/release.yml
  - scripts/check-version-bump.mjs
verified_against: 2fcc5f24a7e4…
PLAIN ENGLISH

This note's identity — its filename and the name other notes use to link to it.

What kind of thing it describes: a pipeline, a process that runs in stages.

"Here are the exact files I make claims about" — the note's scope, no more and no less.

The recipe that publishes a release…

…and the script that refuses code changes arriving without a version bump. Only the files whose claims moved here — the parent keeps listing the files it still describes.

"…and every claim above was checked against the project exactly as it stood at this snapshot." This is the pin the freshness gate verifies forever after: if either source file changes later, the gate flags this note as stale.

🔍
Verified means re-read, not copied

Moving a paragraph is easy; the discipline is that every moved claim was re-checked against the actual code before the child's pin was written. The project's rule is blunt about why: a dishonest pin is worse than a stale note — it converts "possibly outdated" into "certified wrong."

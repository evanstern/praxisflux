TASK-50 — The Wiki Takes Its Own Medicine
Module 1

Measure Before You Rewrite

The task everyone saw coming — and the audit that changed its shape

TASK-49 built the machinery: a generator for the wiki's summary binder (CAPSULES.md) and size checks inside the project's gate — but it shipped with the safety on. Until a wiki generates its binder, the checks only warn. TASK-50 is the adoption task: make this project's own wiki obey the two size limits (every note blurb under 500 characters, every note body under 8,000), then generate the binder and let enforcement go live.

The task's contract predicted the work: "several descriptions exceed the 500-char budget, and build-and-release.md is 11,742 characters." So the first move was not to start rewriting — it was to measure everything first, using the exact same measuring functions the gate itself uses.

📏
Same ruler as the referee

The audit imported noteBody and the blurb-reading helper straight from the gate's own module. If you measure with your own ruler, you can pass your audit and still fail the referee's. Borrowing the enforcer's ruler makes that disagreement impossible.

The whole audit, six lines

One small script walked all 25 notes and reported anything over either limit:

the measurement pass (simplified) 

for (const file of noteFiles("docs/wiki")) {
  const note = read(file);
  const blurb = description(note).length;
  const body = noteBody(note).length;
  if (blurb > 500 || body > 8000) report(file, blurb, body);
}
PLAIN ENGLISH

Go through every note in the wiki, one at a time — using the gate's own list of what counts as a note.

Open the note.

Measure its blurb — the one-line description a reader skims to decide whether the note is worth opening.

Measure its body — everything below the note's header block, again with the gate's own definition of "body".

If either measurement breaks its limit — 500 characters for the blurb, 8,000 for the body — write the note's name and numbers down.

Next note.

Module 2

One Note, Split Summary-Style

The 11,742-character note becomes a hub and two children — nothing deleted, everything findable

The oversized note, build-and-release.md, described the project's entire build-and-release story in one file: packaging, catalogs, version rules, CI, publishing, and the surface other projects consume. The wiki contract's fix is called a summary-style split: move coherent subtopics into new child notes, and leave a short summary plus a link where each one used to be.

The judgment call is the word coherent. You split by subject, not by arithmetic — and the contract forbids children with less than about 1,500 characters of real substance, so you can't hit the number by scattering confetti. Two natural children emerged:

🚀

release-pipeline

The merge-to-main mechanics: the version-bump rule on changed code, the checks every proposal runs, and the publish-then-tag ordering that makes releases safe to automate.

📦

gates-consumption-surface

How other projects run this project's checks: the installable package, the plug-in CI action, and the exit-code contract they share.

The parent kept everything else — packaging, catalog, version sync — plus one summary paragraph and a link per child. Each child links back. The wiki's table of contents gained exactly two lines, added without rearranging anything that existed. After the split: parent 7,635 characters, children 4,437 and 3,494. All under the cap, each child well over the substance floor.

A child note is born with its own passport

In this wiki, every note must prove itself: it lists the code files it describes and the exact project snapshot its claims were last checked against. A child can't inherit the parent's paperwork — it gets its own, listing only its files:

release-pipeline.md — the header (abridged) 

name: release-pipeline
kind: pipeline
sources:
  - .github/workflows/release.yml
  - scripts/check-version-bump.mjs
verified_against: 2fcc5f24a7e4…
PLAIN ENGLISH

This note's identity — its filename and the name other notes use to link to it.

What kind of thing it describes: a pipeline, a process that runs in stages.

"Here are the exact files I make claims about" — the note's scope, no more and no less.

The recipe that publishes a release…

…and the script that refuses code changes arriving without a version bump. Only the files whose claims moved here — the parent keeps listing the files it still describes.

"…and every claim above was checked against the project exactly as it stood at this snapshot." This is the pin the freshness gate verifies forever after: if either source file changes later, the gate flags this note as stale.

🔍
Verified means re-read, not copied

Moving a paragraph is easy; the discipline is that every moved claim was re-checked against the actual code before the child's pin was written. The project's rule is blunt about why: a dishonest pin is worse than a stale note — it converts "possibly outdated" into "certified wrong."

Module 3

Flipping the Switch

Why the binder had to be generated last — and what changed the moment it landed

Remember the adoption rule from TASK-49: the size checks stay warn-only until a wiki has a CAPSULES.md. The moment that file exists, the same checks become hard failures. That makes the binder a live switch — and the order of operations stops being a style choice:

💥

Generate first: red

Adopt while the fat note still exists and the gate turns strict immediately — every commit from then until the split lands is blocked.

✅

Conform first: green

Measure, split, re-pin — all under warn-only rules — and generate the binder as the last content step. Every intermediate commit passes.

This matters because the project's own hooks run the full gate suite before every commit. A sequencing mistake wouldn't just look bad in the history — it would physically refuse to commit. TASK-50's slices were ordered so the wall never went up in front of unfinished work: audit → split → honest pins → then adopt.

The moment of adoption

One command generated the binder — 27 entries now, including the two new children — and the very next gate run was the strict one:

generate, then prove (verbatim) 

$ node grounding-wiki/scripts/capsules.mjs . docs/wiki
regenerated docs/wiki/CAPSULES.md
$ node scripts/run-gates.mjs --gates wiki-freshness
[wiki-freshness] wiki-freshness ok: 27 note(s) fresh
    against their pinned sources
PLAIN ENGLISH

Run the binder generator TASK-49 built — the one writer allowed to touch this file.

It rebuilt CAPSULES.md: one blurb per note, in table-of-contents order, stamped with the exact project snapshot it was generated at.

Now run the freshness gate — which, seeing the binder exists, enforces every size budget as a hard rule for the first time.

All 27 notes pass: pins fresh, every blurb under 500 characters, every body under 8,000, binder byte-identical to a fresh regeneration…

…and not a single warning line above it. Warned-but-green became simply green — with the strict rules on.

🔒
No exemptions spent

The contract allows a note to declare itself size-exempt with a reason — an escape hatch for the genuinely unsplittable. This wiki adopted with zero exemptions: every note simply fits. The hatch stays unused, which is exactly how you want an escape hatch to stay.

What is different now

Before this task, the wiki's size budgets were advice from a document. After it, they are physics: the machinery TASK-49 built now guards the very wiki that built the machinery. Any future note edit in this project — by a person or an AI session — hits hard enforcement: an oversized blurb blocks the commit, an oversized body points at the split rule from Module 2, and a forgotten binder regeneration is caught by rebuild-and-compare. The whole change shipped as documentation only: not a line of tooling was touched, no version was bumped, and the checks proved it — the full test suite, the docs-sync check, and the freshness gate, green at every one of the five commits.

There is also a quieter payoff. The binder this wiki now maintains is the cheap whole-corpus view the contract promised: a reader — human or AI — who needs to orient across all 27 notes reads one small file instead of 130,000 characters of note bodies, and routes to the two or three notes the task at hand actually needs.

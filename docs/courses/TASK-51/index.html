TASK-51 — Teaching the Readers to Skim
Module 1

A Rule Nobody Read

The rulebook said "don't read everything" — and every reader kept reading everything

The previous task in this story (TASK-48) fixed an expensive habit on paper. This project keeps a grounding wiki, and its shared rulebook — the corpus spec — gained a whole section on how readers should load a wiki: start from the table of contents, fetch only the notes you need, and take the cheap summary sheet when you genuinely need the whole picture.

One problem. A rulebook only changes behavior when it's in front of the reader at the moment they act. The readers here are AI sessions and two orchestration tools — and none of their standing instructions said a word about the new protocol. The rule existed; nothing delivered it.

📕
TASK-51 in one sentence

Take the loading protocol out of the rulebook nobody consults mid-task and write it into the three places readers actually look: every project's always-on instructions, and the two tools that read whole wikis for a living.

The rule that needed delivering

This is the protocol the spec defines — the four habits every wiki reader is supposed to have. TASK-51's whole job is making three real consumers state them.

SPEC v2 — HOW CONSUMERS LOAD A CORPUS 

1. INDEX.md first, always — it is the routing surface.
2. Notes just-in-time, individually. Bulk-loading is never default behavior.
3. Whole-corpus orientation reads CAPSULES.md, not the note bodies;
   where a v1 corpus has no CAPSULES.md, fall back to INDEX + just-in-time.
4. Within a note, ## sections are the addressable unit.
PLAIN ENGLISH

Always open the table of contents first, and let it point you to the right note.

Fetch notes one at a time, only when the task needs them — never photocopy the whole library "to be safe."

When you genuinely need the whole picture, read the summary sheet — CAPSULES.md, one capsule per note, roughly a tenth the cost of the full notes…

…and if an older wiki has no summary sheet yet, just use the table of contents plus one-note-at-a-time. The protocol never requires the new file.

Inside a big note, you may read just the one section you need instead of the whole file.

Module 2

The Always-On Reminder

Four lines added to the note that every session reads before doing anything at all

Every project set up with this plugin suite carries a CLAUDE.md — standing instructions the AI reads before every conversation. The suite's installer, bootstrap, plants a marked block into that file: the rules that hold even when no specialized tool is running.

That block is the one place a rule is guaranteed to be in front of every session, every time. So TASK-51's first change is the smallest and the most important: the loading protocol, compressed to four lines, added to the planted block's "rules that always hold."

⚖️
Why only four lines?

Always-on context is read every single session — it pays its own token cost forever. A rule about saving tokens that itself burned hundreds of them per session would be self-defeating. Compactness here isn't style; it's the rule practicing what it preaches.

The four lines, translated

Here is the new rule exactly as it now appears in every bootstrapped project's always-on block:

PDLC/TEMPLATES/CLAUDE.MD — PLANTED BLOCK 

- Corpus loading: when a grounded corpus is present, load its
  INDEX.md first and route; load notes just-in-time — never bulk-load
  the corpus. Whole-corpus orientation reads CAPSULES.md when it
  exists; without one, INDEX plus just-in-time notes.
PLAIN ENGLISH

If this project has a knowledge base, start every lookup at its table of contents and let that route you.

Pull individual notes only at the moment you need them — reading the whole library up front is never the default.

Need the full picture? Read the cheap summary sheet when the wiki has one…

…and when it doesn't (older wikis), the table of contents plus one-note-at-a-time is the correct fallback.

One subtlety: the block is machinery, not just text. The installer stamps it between markers, detects when a project's copy has drifted from the current template, and never overwrites drifted text without consent. Editing the template meant respecting those markers — the task's tests verify the block's structure survives intact.

Module 3

Two Big Readers Learn to Skim

The tools that legitimately need the whole picture — and the summary sheet that makes that affordable

Most readers need two or three notes. Two tools in this suite are different — their jobs genuinely start with the whole corpus:

Sweep is the board-sweep orchestrator. Before it can plan a batch of tasks, it has to understand the project those tasks touch — that's whole-corpus orientation, and it happens again after every merge, when the orchestrator re-grounds.

Reorient is the direction-evaluation loop. Every evaluator it dispatches must judge research against the project as it actually is — which used to mean each of N parallel evaluators loading the wiki's full note bodies. The corpus cost, multiplied by N, every round.

💊
The capsule bargain

Spec v2's summary sheet — CAPSULES.md, one routing-grade capsule per note — is about a tenth the cost of the full bodies. The new instruction in both tools: take the capsule view for orientation, and open a full note only for what you actually engage with — the concepts a task touches, the claims a report cites.

The evaluator's new marching orders

Here is the changed instruction inside reorient — the "beat" every dispatched evaluator follows. Sweep's orientation moments got the same treatment in its own words.

REORIENT/SKILLS/REORIENT/SKILL.MD — THE BEAT 

ground against the project wiki via its CAPSULES.md when present —
the whole-corpus capsule view — loading a full note only for claims
the report actually cites; absent a rollup, route from INDEX.md and
load notes just-in-time (README/docs when no wiki at all)
PLAIN ENGLISH

When the project wiki has a summary sheet, that sheet is your view of the whole project…

…and you only open a note in full when your report is about to lean on it — a claim you cite deserves the full source; background doesn't.

On an older wiki with no summary sheet, fall back to the table of contents and fetch notes one at a time as needed.

And in a project with no wiki at all, ground yourself on the README and docs — the tool still works, just with weaker guarantees.

🔬
An honestly open question

Does an evaluator grounded on capsules judge as well as one that read every full note? Nobody measured it yet. Rather than guess, the task parked the question inside the skill: the next reorient run is told to record which mode its evaluators used and any quality difference observed. A cheaper habit, adopted with its eyes open.

Shipping words like they were code

Nothing in this task compiles — every change is instructions. The project ships instruction changes with the same discipline as code:

Each edited skill's version number was bumped (sweep 0.3.0 → 0.4.0, reorient 0.1.0 → 0.2.0, bootstrap 0.1.0 → 0.2.0 as the template's owner), and the whole marketplace released as 0.14.0 — a version gate enforces this. And because the project's own wiki documents these tools, the notes describing them were re-verified against the new text and re-pinned in the same change — ten notes in all, most of them touched only by the version stamp.

✅
Where this leaves the story

The protocol now lives in all three delivery points: every project's always-on block, sweep's orientation moments, and reorient's evaluator briefs. A sibling task builds the generator that gives every wiki its CAPSULES.md — and thanks to the fallback wording, these consumers behave correctly whether or not that file exists yet.

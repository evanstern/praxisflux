Module 1

The Plan That Survives Amnesia

One day in July 2026, a game project called promptworld finished a big re-think of its user interface and ended up with a stack of decided tasks on its board. The direction was settled; nobody needed to debate what to build anymore. What remained was the grind: take each task through a spec, an implementation, a PR, a merge, and a documentation refresh — times ten, some in parallel, without breaking each other.

Here’s the catch: the AI session doing that orchestration has a context window. A sweep this size outlives any single session. The session that plans the work in the morning will not be the session that merges the last PR days later — and the next session remembers nothing. Whatever the plan is, it has to survive total amnesia.

📔
Good to know: bottled from a real run

The promptworld session solved this live: it wrote its marching orders into a file — a runbook — and later sessions executed from that file, across days. TASK-45 bottled that working practice into a reusable skill, pdlc:sweep, the same way a good recipe gets written down only after the dish has actually been cooked.

A shift-change handover, in writing

Think of a hospital shift change. The outgoing nurse doesn’t recite the ward’s whole state from memory and hope — there’s a handover binder, and the incoming shift runs from the binder. The sweep skill works the same way, with exactly two artifacts of record: the board (which tasks exist and what each one says — never duplicated anywhere else) and the runbook (the order to do them in, the rules of the road, and a log of what’s done). Here is the runbook template’s actual opening — the words the next session wakes up to:

TEMPLATE — pdlc/skills/sweep/templates/runbook.md 

**You (the session reading this) are the ORCHESTRATOR** for the tasks below. Run each
through the host project's full PDLC — spec → link → worktree → delegated implementation →
PR → merge → re-ground — parallelizing within lanes, merging serially, treating merge
conflicts as routine. Direction is decided; do not re-litigate it: {{DIRECTION_SOURCES}}
win. Plan-of-record is the board; this file carries only ordering, doctrine, and the log.
PLAIN ENGLISH

The file speaks directly to whoever opens it: “you, reading this, are now in charge of running these tasks.” It assumes its reader remembers nothing.

Each task travels the project’s full development lifecycle: write a plan, connect it to the board, build in an isolated copy, hand the coding to a helper…

…then propose the changes, fold them in — several tasks may be built at once, but they are folded into the shared code one at a time, and collisions are expected, not emergencies.

The big questions are already answered — the documents that decided them (named here) outrank any second-guessing.

And a division of labor: the board owns what the tasks ARE; this file owns only the sequence, the rules, and the diary.

The skill states its design test in one sentence: a fresh session must be able to resume the sweep from the runbook plus the board alone. If a decision lives only in chat, the next session doesn’t have it — so it may as well not exist.

Three things a sweep refuses to do

The skill is defined as much by its refusals as by its powers. A sweep does not decide direction — the tasks arrive already decided (from a re-think session, a milestone, or the owner’s explicit list), and a sweep that catches itself re-debating scope must stop and send the question back where it came from. It does not skip the per-task rigor — every substantial task still gets its own spec-and-plan cycle; the sweep just runs that loop ten times instead of once. And it does not write code: implementation is always handed to a separate worker session, while the orchestrator’s hands touch only plans, the board, plumbing, and docs.

💡
Key insight: the conductor doesn’t play an instrument

An orchestrator that starts implementing “just this one small task” inline has quietly become a worker — and nobody is conducting anymore. Keeping the layers separate is what lets one session credibly oversee ten tasks: it plans, dispatches, and checks; it never disappears into the weeds of any single task.

Check your instincts

Mid-sweep, the operator and the session agree in chat to postpone one task. The session ends. What must be true for tomorrow’s session to honor that decision?

To be extra safe, an author pastes every task’s full description into the runbook “so it’s all in one place.” Good idea?

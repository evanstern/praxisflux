Module 2

Many Hands, One Runway

Authoring a runbook starts with one question: which tasks can safely happen at the same time? The sweep’s answer is an airport’s: any number of planes can be in the air at once, but there is only one runway. Develop in parallel, merge serially. Building several tasks side by side is cheap — each gets its own worktree — but landing them into the shared code one on top of another is where collisions happen, so merges queue up and land one at a time.

The author reads every input task, the design document that produced them, and the project’s own rulebook, then sorts the tasks into lanes — groups ordered by dependency. Three placement rules do most of the work: tasks that touch the same files share a lane (and merge smallest-first); the single biggest task gets a lane where nothing fights it for files; and low-priority polish goes in a tail lane that can be dropped without breaking anything.

What a lane actually looks like

One placement rule deserves its own paragraph: contract-shaped work goes first. If task A publishes an interface that tasks B and C will consume, A’s contract unblocks them even while A’s internals are still being built — like pouring a doorframe before the walls are painted. Here is the lane skeleton from the shipped template, with that rule baked into its example entry:

TEMPLATE — pdlc/skills/sweep/templates/runbook.md 

**Lane 1 — start immediately, in parallel:**
- **TASK-{{n}} ({{tier}} — {{rubric justification}})** — {{one-line scope; note if only
  its CONTRACT blocks others while implementation can lag}}
// … lanes 2 through N-1 elided — each opens “after {{condition}}” …
**Lane N — tail (droppable):**
PLAIN ENGLISH

The first lane needs nothing — every task in it can start the moment the sweep begins, all at once.

Each entry names the task, which strength of AI worker it gets (and the written reason why)…

…and flags the doorframe case: when only this task’s published interface blocks the others, the lane behind it can open before the task is fully finished.

Middle lanes are trimmed here for the lesson — each states the condition that unlocks it.

The last lane is the nice-to-haves: droppable without breaking anything if the sweep runs out of road.

Lanes are only part of what the author derives. The runbook also enumerates the project’s per-PR gates (so a dispatched worker can’t miss one), a per-task model tier from the host project’s own rubric, the known conflict hotspots, the checkpoints where a human must be asked, and a checkable definition of done.

Conflicts are weather, not accidents

The runbook assumes something most plans politely ignore: other sessions are working the same repository at the same time. So it writes down conflict doctrine like a pilot’s weather rules. On a merge conflict: replay your branch on top of the current shared code (never tangle the histories together), keep the shared side for anything you didn’t deliberately change, and re-run every gate afterward. When your open PR collides with another session’s, the smaller one lands first — regardless of whose it is. And before diagnosing “my branch broke,” check whether the shared code simply moved underneath you — it usually did.

🌦️
Good to know: written down because nobody will have watched

The doctrine section exists for the amnesia reason again: the session executing lane 3 next week won’t have watched this week’s conflicts happen. Naming the actual hotspot files and the reconciliation rules in the runbook is how hard-won conflict experience survives the shift change.

Check your instincts

Two queued tasks both rewrite the same rendering file. One is large, one is small. How does the author lay them out?

Task A defines a new data format that tasks B and C will consume. A’s full implementation will take days. When can B and C start?

A worker’s branch passed all gates yesterday. Overnight, two sibling tasks merged. The branch is replayed onto the current shared code. Can its PR merge now?
